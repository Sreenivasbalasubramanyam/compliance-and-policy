# Transaction Compliance Monitoring & Rule Engine

A configurable, YAML-driven transaction monitoring rule engine that screens
financial transactions against illustrative internal policy rules and
regulatory-style thresholds.

> **DISCLAIMER - READ FIRST:**
> - All transaction, account, and counterparty data in this repository
>   (`data/synthetic_transactions.csv`) is **entirely SYNTHETIC / FABRICATED**,
>   generated by `data/generate_transactions.py` for portfolio demonstration
>   purposes only. No real customer, account, or transaction records are used.
> - The rule thresholds in `config/policy_rules.yaml` (e.g. the $10,000
>   large-transaction figure) are loosely modeled on the *shape* of real-world
>   concepts such as U.S. Bank Secrecy Act structuring rules and Currency
>   Transaction Report (CTR) thresholds, purely to make the example realistic.
>   **They are illustrative only, are NOT legal/regulatory advice, and are NOT
>   sourced from any real institution's policy.**
> - The "watchlist" used for keyword screening (`src/watchlist_sample.py`) is an
>   **obviously fake, made-up sample list** of fictitious entity names. It is
>   **NOT** a real sanctions or watchlist data source (not OFAC's SDN list, not
>   a UN list, not any government or institutional list) and must not be
>   treated as one.

## Problem Statement

Financial institutions are required to screen transactions against internal
risk policies and regulatory expectations - detecting patterns like
**structuring** (breaking large cash transactions into smaller ones to avoid
reporting thresholds), **large cash transactions** that warrant reporting,
unusual **transaction velocity** (potential account takeover or money-mule
activity), and **sanctioned-party / watchlist** exposure. Compliance,
risk, and engineering teams need a rule engine that is:

- **Configurable** — rules and thresholds live in a policy file, not buried in
  application code, so compliance stakeholders can review/adjust them without
  a code change.
- **Auditable** — every flagged transaction produces a structured, explainable
  exception (which rule, why, at what severity).
- **Testable** — each rule has explicit positive and negative test cases.

This project is a small-scale, illustrative version of that kind of
partnership between risk, compliance, and engineering to deliver a
production-shaped (if not production-scale) rule-driven monitoring pipeline.

## Tech Stack

- **Python 3.10+**
- **Pandas** — transaction data handling and windowed rule evaluation
- **PyYAML** — declarative rule configuration
- **Pytest** — unit tests (one positive + one negative case per rule)

## Architecture

```
config/policy_rules.yaml   <--  declarative rule definitions (thresholds, severity)
                                          |
data/generate_transactions.py            |
        |                                |
        v                                v
data/synthetic_transactions.csv  -->  src/rule_engine.py
                                   (evaluates every transaction
                                    against every configured rule)
                                          |
                                          v
                                 structured exceptions
                              (rule_id, severity, txn_id, reason)
                                          |
                                          v
                              src/compliance_report.py
                                          |
                        +-----------------+------------------+
                        v                                    v
          outputs/compliance_exceptions.csv          outputs/summary.txt
              (full exception detail)              (counts by rule/severity)
```

### Rules implemented

| Rule | Illustrative concept | Severity |
|---|---|---|
| `structuring_threshold` | Multiple sub-$9,000 cash transactions aggregating past $10,000 within 24h | high |
| `large_transaction_reporting_threshold` | Single transaction >= illustrative $10,000 CTR-style threshold | medium |
| `velocity_rule` | More than 8 transactions on one account within 24h | medium |
| `watchlist_keyword_screening` | Counterparty name matches a fake sample watchlist keyword | critical |

## How to Run

```bash
# 1. Install dependencies
pip install -r requirements.txt

# 2. Generate the synthetic transaction dataset
python data/generate_transactions.py --accounts 150 --days 14 --seed 7

# 3. Run the rule engine directly (prints exception counts by rule)
python src/rule_engine.py

# 4. Generate the full compliance report (CSV + text summary)
python src/compliance_report.py

# 5. Run the test suite
python -m pytest tests/ -v
```

## Actual Results (from a real test run)

Generated with `--accounts 150 --days 14 --seed 7` (4,327 synthetic transactions
across 150 accounts over 14 days, including deliberately crafted transactions
designed to trip each rule).

```
Total transactions screened: 4327
Total exceptions flagged:    92
Unique accounts flagged:     20

Exceptions by rule:
  - velocity_rule: 63
  - structuring_threshold: 18
  - large_transaction_reporting_threshold: 6
  - watchlist_keyword_screening: 5

Exceptions by severity:
  - medium: 69
  - high: 18
  - critical: 5
```

All 10 pytest cases pass (one "fires on crafted transaction" + one "does not
fire on clean transaction" test per rule, plus two general engine sanity
checks). Full exception-level detail is written to
`outputs/compliance_exceptions.csv`; the human-readable rollup is written to
`outputs/summary.txt`.

## Future Improvements

- Replace naive substring watchlist matching with fuzzy/phonetic matching
  (e.g. Levenshtein distance, Soundex) to better demonstrate real-world
  entity-resolution challenges in sanctions screening
- Add case management workflow states (open / under review / closed / SAR-filed)
  instead of a flat exception list
- Add a configurable "lookback" re-evaluation window so already-reported
  structuring/velocity patterns aren't re-flagged on every run
- Parameterize thresholds per account risk tier (retail vs. business vs.
  high-risk-jurisdiction accounts)
- Add a small Streamlit/dash UI for compliance analysts to triage exceptions
- Add CI (GitHub Actions) running `pytest` on every push
